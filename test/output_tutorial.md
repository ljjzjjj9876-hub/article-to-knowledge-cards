# 知识卡片：写一条好的 Git 提交信息

## 卡片 1｜为什么要写好提交信息
- **核心知识**：好的提交信息能让未来的你或队友快速理解这次改动做了什么、为什么做。
- **简明解释**：提交信息是给“读的人”看的，几个月后靠它就能还原改动意图，减少逐行看代码的成本。
- **自测问题**：写好提交信息最重要的受益者是谁？答案：未来的你和队友。

## 卡片 2｜提交信息的格式
- **核心知识**：常用格式是“主题行 + 正文”，主题行用祈使语气说明做了什么，正文解释为什么这么做。
- **简明解释**：主题行一句话、不超过 50 个字符，用祈使语气（如“fix: …”）；正文在主题行下方空一行，说明背景、决策和替代方案，不重复代码本身。
- **例子**：主题行“fix: 修复登录页在移动端错位的问题”，正文里再写错位原因和为什么这样修复。

## 卡片 3｜类型前缀
- **核心知识**：常见类型前缀有 feat、fix、docs、refactor、test、chore。
- **简明解释**：feat 是新功能、fix 是修缺陷、docs 是文档、refactor 是重构（不改变功能）、test 是测试、chore 是构建或杂务；统一前缀让提交历史一眼看出性质。
- **自测问题**：新增一个功能，提交信息类型前缀应该用什么？答案：feat。

## 卡片 4｜原子提交
- **核心知识**：一次提交只做一件事，一个逻辑改动且能独立通过测试。
- **简明解释**：不要把修 bug 和加新功能混在一次提交里，否则难定位、难回滚；原子提交改动独立、可单独验证。
- **自测问题**：一次提交里同时修复了两个 bug，是否符合“原子提交”？答案：否，应拆成两次。

## 卡片 5｜核心原则：站在读者角度
- **核心知识**：写提交信息的核心是站在读的人角度，让 git log 里只看信息就能理解改动内容和原因。
- **简明解释**：以读者能否理解为准，能理解就是好提交；这是贯穿格式、类型、原子性的总原则。
- **例子**：打开 git log 看到“fix: …”+ 正文原因，不用翻代码就知道发生了什么，即为好的提交信息。

> 说明：原文约含 5 个独立知识点，数量达标，无重复需合并。
